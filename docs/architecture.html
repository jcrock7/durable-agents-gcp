01Summary

AI agents that finish the job, safely and on budget.

A reference platform for running AI agents in Google Cloud platform. Runs survive failures, every model call is governed and costed, and no credential lives in application code. The whole environment comes up from one command and is torn down when idle.

Reliability 0steps lost

By design, a crashed or evicted worker resumes from its last completed step.

Cost governance $0.10per hour

Estimated infrastructure cost while running. Per-agent budgets cap model spend.

Security 1identity

Only one service account can call a model. One public entry point, behind Google sign-in.

Delivery 1command

Terraform builds and destroys the environment. Evals gate every change before it merges.

03Components

Every part earns its place, and each choice is on record

What each component does, why it was chosen over the alternatives, and the design principle it enforces.

Gateway + IAP

Public edge
Function

The only public entry point. Terminates TLS and requires a Google sign-in before any request reaches the app.

Rationale

No auth code in the application, access granted per user or group, and unauthenticated traffic can't spend the model budget.

No request reaches an agent without an approved Google identity.Decision record 0010 →

API + UI

Spot
Function

Fastify serves the React app and the REST API. It starts workflows, forwards approvals as signals and reads progress with queries.

Rationale

One TypeScript image for UI and API saves a pod, and types are shared with the workers.

The API never runs agent logic. It hands work to Temporal and returns immediately.Decision records 0001, 0013 →

Temporal

On-demand
Function

Durable runtime. Records each step of every agent run as event history, retries failures with backoff, and holds runs that wait for a human.

Rationale

Agent runs are long, multi-step and call unreliable services. For the prototype it's a single dev-server pod with SQLite on a persistent disk.

If a pod dies mid-run, the agent resumes from its last completed step, not from scratch.Decision records 0002, 0011 →

Agent worker

Spot
Function

Runs workflow and activity code for every agent, one task queue per agent. Model and tool calls happen only inside activities, using the Vercel AI SDK.

Rationale

It's stateless, so it runs on Spot. Temporal absorbs Spot evictions without losing work.

Workflows decide, activities act. Only activities touch the network.Decision records 0003, 0013 →

LiteLLM gateway

Spot
Function

One model endpoint. Maps aliases to Vertex models with fallbacks, enforces per-agent budgets, logs cost per request, and screens prompts for injection.

Rationale

Agents hold no cloud credentials, and spend and safety are controlled in one place. Guardrails layer Vertex safety filters, a Flash-Lite injection check, and tool allow-lists in the app.

Every token goes through one door, and that door has a budget.Decision records 0005, 0012 →

Postgres + pgvector

On-demand
Function

App data, agent results, retrieval embeddings, and LiteLLM spend logs, in separate databases.

Rationale

One stateful store; pgvector avoids a separate vector database. Runs on the CloudNativePG operator, with Cloud SQL available behind a Terraform flag.

One database, backed up to Cloud Storage before the cluster is torn down.Decision record 0007 →

Vertex AI

Google-managed
Function

Gemini models plus partner models from Model Garden.

Rationale

IAM-based auth with no keys, one bill, and several model families to route between.

Exactly one service account in the cluster can call a model: the gateway's.Decision record 0004 →

Cloud Trace + Logging

Google-managed
Function

One trace per agent run, spanning API, workflow, activity, gateway and model call.

Rationale

OpenTelemetry keeps instrumentation vendor-neutral. Exporting straight to managed backends means no collector pod.

Every run can be traced end to end: where the time went and what it cost.Decision records 0008, 0013 →

Secret Manager

Google-managed
Function

Holds the gateway master key and database passwords, mounted into pods by the Secret Manager add-on.

Rationale

No secrets in git, images or manifests. The public repo is checked by gitleaks before every commit and again in CI.

The repo is public and contains no secrets, and that's enforced, not just promised.Setup guide, section 4 →

GitHub Actions + promptfoo

Around the cluster
Function

Evals gate every pull request, and a red-team suite tests the guardrails. Authenticates to GCP with Workload Identity Federation.

Rationale

Prompt and model changes break agents silently. Tests make quality visible.

A prompt change that fails the eval suite doesn't merge.Decision record 0009 →

Terraform

Around the cluster
Function

Two layers. A persistent layer (state bucket, registry, secrets, service accounts) stays. An ephemeral layer (network, Autopilot cluster, load balancer) is created when needed and destroyed when idle.

Rationale

Reproducible from scratch, and nothing expensive runs while the platform is idle.

The whole environment comes up from one command and costs around ten cents an hour while it's up.Decision record 0014 →

05Scenarios

How the platform behaves under failure and pressure

The principles behind the design, and the scenarios that verify each one.

Design principles

  1. 01

    Durable by default. Agent runs are long and call unreliable services, so every step is recorded and every run can resume.

  2. 02

    One governed path. Sign-in at the edge, the API hands off to Temporal, the worker does the work, and every model call goes through one gateway.

  3. 03

    Failure is routine. Stateless pods run on Spot capacity. Evictions are expected, and Temporal absorbs them.

  4. 04

    Spend and safety in one place. The gateway enforces budgets, logs cost per run and screens prompts.

  5. 05

    Disposable infrastructure. Terraform creates and destroys the environment. It costs about ten cents an hour while running and close to nothing when idle.

Verification scenarios

  1. 01

    Worker fails mid-run

    Delete the worker pod (kubectl delete pod -l app=worker). The run pauses, a replacement pod starts, and the run continues from its last completed step.

  2. 02

    Prompt injection in retrieved content

    A document the agent reads contains a hidden instruction. The gateway blocks the call and logs the reason.

  3. 03

    Budget exhausted

    An agent reaches its spend limit. The gateway refuses further calls and the workflow stops cleanly with a clear status.

  4. 04

    Risky action needs approval

    The agent pauses before a write. An approval signal resumes the run.

  5. 05

    End-to-end trace

    Each run produces one trace spanning the API, workflow, activity, gateway and Vertex AI call.
