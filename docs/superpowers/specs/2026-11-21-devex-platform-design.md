# Developer Experience and Platform Engineering additions: design

Date: 2026-11-21 · Status: draft for review · Branch: `design/devex-platform`

## Intent

This repo is a portfolio piece for Developer Experience (DevEx) and Platform Engineering roles. It already shows the platform runtime: Terraform for GKE Autopilot, kustomize overlays, k3d mirroring GKE, IAP, cost guardrails, Temporal, MCP and the agent portal. What it doesn't show is the developer's side of the platform: how code gets from a laptop to a running agent, and how a team would build the next agent.

Success means a reviewer can watch one story end to end:

> "Scaffold a new agent → open a PR → CI tests it and runs it in a throwaway preview environment → merge → Argo CD rolls it out → traces, SLOs and DORA metrics show how it and the team are doing → a developer portal ties it all together."

### Goals
- A golden path: one command scaffolds a working agent that passes CI unchanged.
- Fast, trustworthy PR feedback, including an ephemeral end-to-end preview.
- Git as the deploy source of truth (GitOps), which also suits the shutdown-when-idle cluster.
- Observability across API → Temporal → activities → MCP → LiteLLM, with one SLO and DORA metrics.
- Guardrails as code (admission policy, managed secrets) instead of scripts and conventions.
- Every piece explained by an ADR, so the reasoning is part of the demo.

### Non-goals
- Multi-tenant or multi-team org modelling beyond what the catalog needs.
- Production-grade high availability for platform tools (single replicas, spot).
- Replacing Temporal, LiteLLM or MCP choices.

### Anti-goals
- Anything that keeps billing while the cluster is down, beyond cents.
- Tooling that only works on GKE: every component must also run on k3d.
- Demo-ware: each piece must work for real (CI blocks bad PRs, policies reject bad manifests).

## Constraints
- The cluster is created for demo sessions and destroyed afterwards. Every in-cluster component must come back from Git on spin-up, with no hand steps and no state that matters.
- Target added cost: about $0 while the cluster is down (Artifact Registry and Secret Manager cents), and a few cents an hour while it's up.
- The public GitHub repo, so GitHub Actions minutes are free.
- Existing conventions: pinned versions, ADRs in `docs/adr/`, scripts in `scripts/{local,gke,lib}`, kustomize components for optional features (as with `demo-controls`).

## Components

### 1. CI and PR preview environments (GitHub Actions)
- **`ci.yml` on every PR:**
  - `pnpm install --frozen-lockfile`, `pnpm test` (typecheck + vitest), and the web build.
  - `kubectl kustomize` render of both overlays, then policy checks on the rendered YAML: Kyverno CLI with the same policies as item 6, and kubeconform for schema.
  - `terraform fmt -check` and `validate` with no backend.
  - Image builds with layer caching, pushed only on `main` to Artifact Registry through Workload Identity Federation (no keys).
- **`preview.yml` on PRs labelled `preview` (or on every PR, if fast enough):**
  - Create k3d in the runner, build images, and apply the local overlay with `LOCAL_MODELS=mock` (no model spend), then seed the ERP.
  - Run a smoke test: start the sample case through `/api/demo/sample-case`, poll `/live` until it reaches the review gate, approve, and assert it resolves.
  - Upload logs and a Live Run screenshot (Playwright) as artifacts, and comment the result on the PR.
- **Required checks on `main`** (branch protection).
- Cost: $0, plus Artifact Registry storage of about $0.10/GB-month with a keep-last-N cleanup policy.

### 2. GitOps (Argo CD)
- Argo CD is installed by the spin-up script (`scripts/gke/up.sh`, `scripts/local/k3d-up.sh`) as the only imperative step after the cluster exists.
- An app-of-apps in `platform/gitops/`: one Application per overlay (`local` follows the working branch, `gke` follows `main`), plus platform add-ons (Kyverno, External Secrets, OpenTelemetry Collector).
- Environment values that come from Terraform outputs today (`cluster.env`) move into a ConfigMap generated by the up script, or into Argo CD's kustomize parameters. This removes the gitignored env files from the deploy path.
- `apply-k8s.sh` stays as a fallback for k3d inner-loop work.
- Demo moment: destroy the cluster, recreate it, and watch Argo CD rebuild everything from Git.
- Cost: about 0.5 vCPU / 1 GiB on spot while up, a few cents an hour.

### 3. Golden path: agent scaffolding
- `pnpm create-agent <name> --pattern <exception|research|remediation>` generates:
  - `agents/general/<name>/` with a workflow, typed activities, an `agent.config.ts` allow-list, a skills folder, prompts with a `PROMPT_VERSION`, and tests (workflow on the time-skipping server, plus an activity test with in-memory MCP).
  - A registry entry in `apps/api/src/registry.ts` and the worker registration.
  - A `LIVE_GRAPHS` entry, so the new agent gets the Live Run view for free.
  - A Backstage `catalog-info.yaml` (item 4).
  - An ADR stub.
- The template lives in `templates/agent/` and is tested in CI: scaffold into a temp dir, `pnpm test`, delete. The golden path can't rot.
- `docs/golden-path.md` covers the five-minute tutorial and the "paved road vs. off-road" rules.
- Cost: $0.

### 4. Developer portal (Backstage)
- A Backstage app in `apps/backstage/`, with an image built in CI and deployed by Argo CD.
- The catalog is defined in YAML in the repo:
  - agents and MCP servers as Components
  - the API as an API entity with its OpenAPI spec, generated from Fastify routes
  - Temporal, LiteLLM and Postgres as Resources
  - owners as Groups
- Rebuilt from Git on every spin-up.
- TechDocs from `docs/` (ADRs, golden path).
- The scaffolder action wraps item 3's template.
- Plugins: a GitHub Actions view per component, Argo CD sync status, and links to the agent portal's Live Run and Agent Health.
- Storage: SQLite in memory, or the CloudNativePG Postgres. Both are disposable, since the catalog comes from Git.
- Cost: about 0.5 vCPU / 1.5 GiB on spot while up.
- **Open question:** Backstage adds a large TypeScript app to maintain. A lighter "Catalog" tab in the existing portal, driven by the same YAML, is the alternative (see Approaches).

### 5. Observability (OpenTelemetry)
- Implements ADR-0008, which is currently deferred.
- OpenTelemetry SDK in the API, worker and MCP servers. The Temporal TS SDK interceptors propagate trace context through workflows and activities.
- A traceparent header on MCP and LiteLLM calls.
- An OTel Collector, deployed by Argo CD, sends:
  - on GKE: traces to Cloud Trace and metrics to Google Managed Prometheus
  - on k3d: to a local Jaeger and Prometheus (or the Collector's debug exporter)
- **One SLO:** "95% of cases reach a decision point (review gate or resolution) within 2 minutes", with a burn-rate alert.
- **DORA metrics** computed from GitHub (PRs, merges, workflow runs, reverts) by a scheduled Action that commits a JSON snapshot. Shown on a portal page and in Backstage. This keeps them independent of cluster lifetime.
- The Live Run drawer links each step to its trace.
- Cost: free tiers at demo volume.

### 6. Guardrails: policy and secrets
- **Kyverno admission policies** (also run in CI):
  - pinned image digests or tags, no `:latest`
  - resource requests and limits
  - required labels (`app.kubernetes.io/name`, owner)
  - no privileged pods
  - NetworkPolicy present per namespace
  - the `demo-worker-killer` Role may only be bound in overlays with the demo component
- A ValidatingAdmissionPolicy that limits the demo Role's pod deletes to `app.kubernetes.io/name=worker`. This closes a deferred finding from the Live Run review.
- **External Secrets Operator → Secret Manager** replaces `load-secrets.sh` and script-created Secrets. Passwords are generated once in Secret Manager by Terraform and survive cluster teardown.
- Cost: Secret Manager cents a month; Kyverno and ESO a few cents an hour while up.

### 7. Inner loop (optional)
- A dev container (Node 24, pnpm, kubectl, k3d, kustomize, terraform, gcloud), so a new contributor is productive in one click.
- Tilt (or `skaffold dev`) against k3d: rebuild and redeploy on save.
- Cost: $0.

## Approaches considered (for the review to settle)

| Decision | Option | Trade-off | Recommendation |
|---|---|---|---|
| Developer portal | **Backstage** | The recognised tool and a strong signal for this role, but heavy to maintain | Backstage, kept minimal (catalog, TechDocs, scaffolder) |
| | Catalog tab in the existing portal | Cheap, on-brand, less recognisable | |
| GitOps tool | **Argo CD** | Rich UI for demos | Argo CD |
| | Flux | Lighter, no UI | |
| Policy engine | **Kyverno** | YAML policies, a CLI for CI | Kyverno + ValidatingAdmissionPolicy |
| | Gatekeeper / OPA | Rego, more general | |
| PR previews | **k3d in GitHub Actions** | $0, but slower (about 8–12 min) | k3d in Actions |
| | Namespace-per-PR on GKE | Faster and more realistic, but needs the cluster up | |

## Build order
Each step is independently demoable:
1. **CI** (item 1, without previews), plus branch protection.
2. **Golden path** (item 3), tested in CI.
3. **PR previews** (item 1), which reuse the demo endpoints and mock models.
4. **GitOps** (item 2), including teardown and rebuild from Git.
5. **Observability** (item 5): traces first, then the SLO, then DORA.
6. **Guardrails** (item 6).
7. **Developer portal** (item 4).
8. **Inner loop** (item 7).

Each step gets its own ADR, its own plan (writing-plans), and its own PR.

## Cost summary
| | Cluster down | Cluster up (per hour) |
|---|---|---|
| CI, previews, scaffolding, DORA snapshot, dev container | $0 | $0 |
| Artifact Registry and Secret Manager | under $1/month | – |
| Argo CD, Kyverno, ESO, OTel Collector, Backstage (spot) | $0 | about $0.05–0.10 combined |
| Cloud Trace and Managed Prometheus | free tier | free tier |

These are estimates from Autopilot per-pod pricing. Reconcile them against the billing export after the first session that runs these components.

## Left to each step's plan
- Exact versions, pinned and at least two weeks old.
- The DORA calculation details: what counts as a deployment, and how failures are detected.
- Backstage plugin selection beyond the three named.
- Whether previews run on every PR or only on labelled ones, decided by measured runtime.
