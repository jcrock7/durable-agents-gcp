# Platform services

The three shared services every agent depends on, as Kustomize bases. They aren't applied on their own: the environment overlays in [`platform/k8s/overlays`](../k8s/overlays/) include them and add what differs between k3d and GKE.

| Service | What runs | Capacity | Decision records |
|---|---|---|---|
| [`postgres/`](postgres/) | CloudNativePG operator (cluster-wide) and one Postgres 17 instance, `agents-pg`, with pgvector. Databases `app` and `litellm`, each with its own role | On-demand, 5 Gi disk | [0007](../../docs/adr/0007-postgres-pgvector.md) |
| [`temporal/`](temporal/) | Temporal CLI dev server: gRPC on 7233, Web UI on 8233, SQLite history on a 1 Gi volume | On-demand | [0002](../../docs/adr/0002-temporal-durable-runtime.md), [0011](../../docs/adr/0011-temporal-single-pod.md) |
| [`litellm/`](litellm/) | LiteLLM gateway on 4000: model aliases `fast` and `smart` on Vertex AI, Vertex safety filters, fallback smart → fast, spend logs in Postgres, prompt-injection guardrail | Spot on GKE | [0005](../../docs/adr/0005-llm-gateway-litellm.md), [0012](../../docs/adr/0012-guardrails-lightweight.md) |

All images are pinned by version and digest. Versions as of this build: CloudNativePG 1.30.1, `postgresql:17-standard-bookworm`, Temporal CLI 1.10.0, LiteLLM 1.106.6 (the official `litellm-non_root` image).

Every service runs as a non-root user with privilege escalation off and all Linux capabilities dropped, so they pass the `restricted` Pod Security standard, which the namespace enforces: a pod that doesn't comply is rejected. Temporal and LiteLLM also use a read-only root filesystem, with `/tmp` as their only writable path besides their data volumes.

## How environments differ

| | k3d (`overlays/local`) | GKE (`overlays/gke`) |
|---|---|---|
| Secrets | Random values generated once and kept in the cluster | Read from Secret Manager (generated by the foundation Terraform) |
| LiteLLM → Vertex AI | Your Application Default Credentials, mounted from a local-only Secret | Workload Identity as `wl-litellm` (the only identity with Vertex AI access) |
| LiteLLM placement | Any node | Spot, 25s shutdown |
| Postgres backups | None | WAL archived continuously and a base backup before teardown, to `gs://<project>-pg-backups/agents-pg/<cluster-created-time>/`, as `wl-postgres` |

Secrets are synced into Kubernetes Secrets by the apply scripts (`pg-app`, `pg-litellm`, `litellm`), because CloudNativePG and LiteLLM read credentials from Secrets and environment variables. The GKE Secret Manager add-on stays enabled for workloads that want secrets mounted as files.

## Apply

```bash
scripts/local/apply-k8s.sh     # k3d
scripts/gke/apply-k8s.sh       # GKE, after scripts/gke/up.sh
```

Both scripts install the CloudNativePG operator first (its custom resources must exist before `Cluster` and `Database` are applied), create the secrets, apply the overlay, and wait for Postgres, Temporal and LiteLLM.

## Using the services

| Task | Command |
|---|---|
| Temporal Web UI | `kubectl -n agents port-forward svc/temporal 8233:8233`, then open http://localhost:8233 |
| Call LiteLLM | `kubectl -n agents port-forward svc/litellm 4000:4000`, then `curl localhost:4000/v1/chat/completions -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' -d '{"model":"fast","messages":[{"role":"user","content":"hi"}]}'` |
| LiteLLM master key | `kubectl -n agents get secret litellm -o jsonpath='{.data.master-key}' \| base64 -d` |
| Postgres shell | `kubectl -n agents exec -it agents-pg-1 -- psql app` |
| LiteLLM Admin UI | With the LiteLLM port-forward running, open http://localhost:4000/ui and sign in as `admin`. First time on a cluster: set the password with the invitation link `apply-k8s.sh` prints |
| Postgres status | `kubectl -n agents get cluster agents-pg` |

Inside the cluster, apps use `temporal:7233`, `http://litellm:4000` and `agents-pg-rw:5432`.

## The prompt-injection guardrail

[`litellm/config/prompt_injection.py`](litellm/config/prompt_injection.py) runs before every chat request. It sends the untrusted parts of the conversation (user messages and tool results, which include retrieved documents) to the `fast` model with a strict JSON prompt, and rejects the request with HTTP 400 if the model reports an injection attempt. If the classifier itself fails, the request continues by default and a warning is logged. Set `GUARDRAIL_FAIL_CLOSED=true` in `litellm-env` to block instead.

Tests run inside the pinned LiteLLM image:

```bash
docker run --rm -v "$PWD/platform/services/litellm:/svc" -w /svc --entrypoint python \
  ghcr.io/berriai/litellm-non_root:v1.106.6 -m unittest discover -s tests -v
```

## Things to check and maintain

- **Model IDs** (`LITELLM_FAST_MODEL`, `LITELLM_SMART_MODEL` in `litellm/kustomization.yaml`) change as Google releases and retires models. Defaults are `gemini-3.5-flash-lite` and `gemini-3.5-flash` on the `global` location (`VERTEX_LOCATION`); in November 2026 this project got 404 for every Gemini model in `us-central1`. To see what your project can call, try `generateContent` against `https://aiplatform.googleapis.com/v1/projects/<project>/locations/global/publishers/google/models/<model>`.
- **CloudNativePG backups** use the operator's built-in Barman Cloud support, which is deprecated and will be removed in 1.31. Move to the Barman Cloud plugin before upgrading past 1.30.
- **Restoring a backup** into a new session is manual for now: create the new cluster with `bootstrap.recovery` pointing at the previous session's folder in the backup bucket.
- **Upgrading images:** change the tag and digest together (`docker buildx imagetools inspect <image>:<tag>` prints the digest), and prefer releases that have been out for at least two weeks.
